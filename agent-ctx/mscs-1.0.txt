Controlled use principles
 MSCS documents may be shared with clients as part of 11-11 Tech engagements or under separately agreed commercial
terms.

 Internal client use does not automatically grant the right to resell, republish, rebrand or create a competing commercial
certification product from the framework.

 Capability IDs are stable framework references. Projects may extend MSCS with project-specific controls, but should not
redefine canonical IDs.

 MSCS certification is an 11-11 Tech framework determination. It does not replace ISO certification, statutory approval,

 Trademark, patent or other formal registrations are separate legal processes. The framework should be reviewed by qualified
counsel before commercial licensing terms are finalized.

EXECUTIVE STANDARD

What MSCS changes
MSCS turns architecture completeness from an opinion into a versioned, addressable and evidence-backed control
system.

Figure 1 — MSCS is designed as both a standard and a product platform.

UDPCS 1.0 provides the broad capability map used to discover what a digital company may need. MSCS 1.0 is the
normative companion: it assigns durable IDs, profiles, evidence requirements, audit states, certification gates and
governance rules so those capabilities can be assessed consistently across projects.
CORE DOCTRINE

A product capability is not complete merely because its UI or backend exists. It is complete when the required experience,
control, platform, operations and governance responsibilities are defined, implemented and evidenced for the project’s declared
maturity.

NORMATIVE CORE

Language, scope and non-negotiable principles
MSCS uses explicit normative language so teams, auditors and automation can reach the same interpretation.
Word

Meaning

MUST / REQUIRED

Mandatory for conformance when the control applies to the target profile.

MUST NOT

Prohibited condition; violation is a blocker unless the control is legitimately not applicable.

SHOULD

Strong recommendation. Deviation requires documented rationale when material.

MAY

Permitted implementation choice.

N/A

Not applicable only with a documented reason. N/A is not a synonym for “not built yet”.

FUTURE

Explicitly deferred capability outside the current target maturity; cannot be used to defer a control required
by the declared profile.

Foundational principles
 Capability identity is stable: canonical IDs are immutable once issued.
 Applicability is explicit: every control is Required, Conditional, Optional, Not Applicable or Future.
 Authority is exact: certification attaches to a defined project, version/release, environment and evidence state.
 Proof is stronger than claim: implementation, tests, runtime and operational evidence are distinct assurance classes.
 Critical failures override percentages: a 95% score cannot hide an unproven payment, identity, privacy, backup or privilegedadmin control.

 Agent authority is separate from API authority: exposing an API never automatically authorizes an AI agent to use it.
 Regulatory readiness is mapped, not invented: M4 does not claim external statutory certification.

M1 / M2 / M3 / M4
A project declares a target profile before assessment. Profiles are cumulative but applicability remains contextual.

Figure 4 — The four MSCS maturity profiles.

Profile

Certification intent

Minimum organizational expectation

The bounded product can legitimately serve early users.

Core user journey; authoritative identity/data; minimum admin control; essential

AUDIT DISCIPLINE

Finding Taxonomy
A real standard must distinguish a product defect from an evidence defect, an authority problem or an external dependency.
Code

Finding class

Definition / treatment

F-IMP

Implementation defect

Required behavior or control is absent, incorrect or insecure. Remediate implementation.

F-EVD

Evidence defect

Capability may exist, but required proof is absent, stale, incomplete or non-reproducible. Remediate evidence/harness.

F-AUTH

Authority / custody defect

Assessment cannot prove the exact branch, release, environment, identity or authorized writer. Stop and recustody.

F-ENV

Environment / external gate

Provider, account, policy window, staging condition or external service prevents valid verification. Do not invent success.

F-POL

Owner / policy decision

Implementation choice requires explicit business/governance authority rather than technical inference.

F-RSK

Accepted risk / exception

Known deviation is formally documented, time-bounded, owned and approved at the required authority level.

Formal dispositions
Disposition

Meaning

PASS

Target profile requirements and mandatory gates are satisfied.

PASS WITH CONDITIONS

No blocking control is unresolved, but time-bounded remediation or monitoring conditions remain.

FAIL

One or more mandatory controls, evidence floors or critical gates fail.

NOT APPLICABLE

Control legitimately does not apply and the rationale is recorded.

CERTIFICATION LOGIC

Score + Mandatory Gates

Indicative weighted threshold

Mandatory conditions

M2

Required design answer

Registry lifecycle rules
 Major version: breaking semantic change to the framework, profile or canonical control meaning.
 Minor version: additive controls, mappings, evidence rules or domain extensions that remain backward compatible.
 Patch version: editorial clarification or metadata correction with no change to control intent.

PRODUCT ROADMAP

From Standard to Platform
The document is release 1 of the IP, not the final product.
Product layer

MSCS deliverable

Commercial / technical value

1 — Standard

Versioned DOCX/PDF specification.

Defines proprietary terminology, control model, profiles, audit logic and certification.

2 — Registry

Canonical JSON/YAML/database control catalog.

Single source of truth for automation, mappings, versions and generated artifacts.

3 — Auditor

CLI / CI / web assessment engine.

Automates applicability, evidence collection, findings and readiness scoring.

4 — Control Plane

Multi-project SaaS dashboard.

Portfolio governance, remediation ownership, evidence expiry, certification and drift.

5 — API

Developer-facing MSCS service.

Integrates readiness controls into client platforms, CI/CD and governance tools.

6 — MCP

Agent-facing MSCS server.

Allows authorized AI systems to query controls, collect evidence and prepare
assessments.

7 — Certification Network

Training, assessor governance and renewal.

Scales delivery while preserving methodology quality and 11-11 Tech brand authority.

GLOSSARY

Canonical MSCS Terms
Defined terms should be used consistently in client deliverables, tooling and certification records.
Term

Definition

Applicable control

A control included in the project scope by required/conditional determination.

Authority

Exact project state against which evidence and certification are valid.

Capability

An ability the product/company must possess and operate.

Certification

Formal MSCS determination for an exact scope/profile/version/environment.

Control

Addressable normative MSCS requirement represented by a canonical ID.

Control Plane

Internal administrative and operational authority over customer-facing capabilities.

Evidence floor

Minimum evidence classes required before a control can reach certification state.

Finding

Documented divergence between requirement/evidence and observed state.

Maturity profile

Cumulative readiness target M1-M4.

Project namespace

Client/project-specific extension IDs that do not redefine canonical MSCS IDs.

Risk exception

Time-bounded, owned, approved deviation with compensating controls.

Runtime evidence

Proof from the actual deployed/executing system rather than source or test intent.

Selected M4 control

A regulated-grade control applied to a lower-profile project because its risk/obligation requires it.

Superseded control

A retired canonical ID replaced by another control while preserving audit history.

11-11 TECH

MSCS 1.0 — The Standard for Declaring Software Architecturally
Complete
MSCS is designed to make completeness auditable, evidence-driven and repeatable across products, clients and industries.
DEFINITION OF ARCHITECTURE COMPLETE

Every applicable capability required for the target maturity has been identified; ownership, control surfaces, dependencies, data, security, operations and governance are
defined; mandatory implementation has been built and objectively evidenced; critical gaps are closed or formally governed; and the exact project authority has passed the
required MSCS certification gates.
