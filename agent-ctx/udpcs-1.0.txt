EXECUTIVE BRIEF

Build the company around the product - not after
it.
A marketplace, CMS or application is incomplete when the public experience works but the business cannot govern,
support, reconcile, secure, audit or extend it.
The recurring failure pattern in software projects is not usually the absence of another screen. It is the absence of an
operating capability: a marketplace with no seller administration, a CMS with no editorial workflow, payments with no
reconciliation, APIs with no developer console, or customer accounts with no privacy/deletion operations.
11-11 TECH DOCTRINE

Every external capability requires an internal control-plane counterpart. If customers can buy, sellers can sell, editors can
publish, developers can integrate, or AI agents can act, the company must be able to authorize, inspect, support, audit, correct,
suspend, recover and report on those actions.

How to use this standard
 Use the 35-domain Master Capability Catalogue as the architecture index for a new product or company.
 Mark each domain REQUIRED, CONDITIONAL, NOT APPLICABLE or FUTURE before implementation begins.
 For every material feature, run the Capability Mirror and the nine-dimension Feature Completeness test.
 Assess maturity at Foundation, Operational, Scalable or Enterprise / Regulated level rather than using a binary “built / not built”
judgement.

 Require evidence. Source code, a design document or a green UI does not by itself prove operational capability.

Scope
UDPCS 1.0 is designed to be reused across marketplaces, content platforms, SaaS products, consumer/mobile applications,
B2B platforms, AI-enabled software, internal systems and regulated digital services. The framework identifies capability
areas; exact legal, tax and regulatory duties remain jurisdiction- and industry-specific.

Marketplace Financial & Trust Controls
Payment processing is not the same as finance, and seller access is not the same as marketplace governance.
MONEY PRINCIPLE

The platform must distinguish company money, seller/provider money, customer refunds, processor balances, fees, taxes, reserves and liabilities. A successful payment
response does not prove that the accounting state is correct.

Control area

Questions that must be answerable

Settlement & reconciliation

Can every provider transaction, transfer, fee, refund and payout be tied to an internal transaction and ledger state?

Seller balances

What is available, pending, reserved, disputed, withheld or already paid?

Disputes

Who owns card-network evidence, customer complaint handling, liability and account consequences?

Fraud / abuse

Can risk cases freeze or limit activity without corrupting transaction history?

Seller compliance

What information is required to sell in each jurisdiction/category, and how is expiry/reverification handled?

Tax

Which party calculates, collects, invoices, reports or remits tax in each supported market?

Support

Can support explain a payout or refund without receiving unrestricted finance/admin access?

API platform
 Authentication and authorization appropriate to user, service and partner identities.
 Scopes/permissions, quotas, rate limits, idempotency, pagination, consistent errors and request/correlation IDs.
 Explicit versioning and deprecation policy, with documented migration paths.
 Machine-readable OpenAPI descriptions for supported HTTP APIs, plus contract and compatibility testing.
 Webhook signing, replay protection, retries, dead-letter handling and observable delivery status.

Developer Console & Portal
 Developer identity, organizations, projects/apps, credential issuance and rotation.
 OAuth client registration, redirect-URI control, scopes, environments and sandbox/test credentials.
 Usage, quotas, request logs, billing where applicable, webhook configuration and secret rotation.
 Quick starts, SDKs, API reference, examples, changelog, migration guides, status and support.

MCP / AI Agent Gateway
 Tool, resource and prompt registries with explicit schemas and ownership.
 User/organization authorization, OAuth, fine-grained scopes and revocation.
 Human approval for consequential actions, with agent identity and complete execution audit.
 Secrets isolation, data-loss prevention, rate/usage limits, sandboxing and policy enforcement.
 Version compatibility, safe tool evolution, observability and emergency disconnect controls.
BOUNDARY

API access and AI-agent access are related but not identical. Agent actions require stronger contextual authorization, consent, approval and audit because an agent can
chain capabilities in ways an ordinary integration may not.

The Nine-Dimension Feature Completeness Test
A UI working in staging is not enough to call a material capability complete.
Dimension

Pass condition

Product

The user-facing journey and expected outcomes work.

Admin

Authorized staff can inspect, approve, correct and control it.

Data

Authoritative data model, ownership, retention and integrity are defined.

Security

Authentication, authorization, abuse cases and secrets are controlled.

Audit

Material actions produce sufficient traceability.

Operations

Monitoring, alerts, runbooks, retries and failure modes are known.

Support

Agents can diagnose and resolve customer issues under scoped permissions.

Compliance

Privacy, legal, tax and regulatory impacts are identified and implemented where applicable.

Measurement

Success, failure, quality and business outcomes are observable.

Example — Seller payout
Dimension

What “complete” looks like

Product

Seller sees balance, payout state and destination.

Admin

Authorized finance/operator can inspect payout and permitted holds/adjustments.

Data

Ledger and provider references tie the payout to transactions and balance movements.

Security

Changing payout destination requires appropriate reauthentication/verification.

Audit

Material changes and payout actions identify actor, authority and before/after state.

Operations

Failures, retries and stuck states are visible and actionable.

Support

Support can explain status without unrestricted finance authority.

Compliance

Identity/tax/market obligations are enforced where required.

Measurement

Payout volume, failure rate, delay and reconciliation exceptions are monitored.

Evidence Model
A capability is only as credible as the evidence proving it operates.
Evidence class

Examples

Weak substitute to avoid

Design evidence

Approved architecture, workflow, policy, role matrix, data model.

A verbal claim that “the backend handles it”.

Implementation evidence

Source, configuration, migrations, infrastructure-as-code, schemas.

A screenshot with no traceable implementation.

Verification evidence

Automated tests, security checks, contract tests, accessibility tests.

Tests weakened to make the build green.

Runtime evidence

Logs, metrics, transaction records, published content, real API response, real device
behaviour.

Mock/demo data presented as production proof.

Operational evidence

Runbooks, incident exercises, restore tests, on-call evidence, support cases.

A document that has never been exercised.

Governance evidence

Approvals, audit events, policy acceptance, licenses, regulator/tax submissions where
applicable.

Unowned policies or expired documentation.

PROOF PRINCIPLE

The higher the risk, the stronger the evidence. A payment, identity, privacy, security or regulatory capability should not be accepted solely because code exists.
